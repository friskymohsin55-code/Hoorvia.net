Git Merge vs Rebase Cheat Sheet: Printable Command Guide

Every Git developer eventually faces the merge-versus-rebase fork in the road, and guessing wrong rewrites history you cannot get back. Merge keeps the truth — every commit exactly as it happened, branch points and all. Rebase tells a cleaner story — your work replayed in a straight line on top of the latest main. Both are correct, but in different places: merge belongs on shared branches where history is a team record, rebase belongs on private branches before a pull request where readability wins. This printable cheat sheet puts the two side by side: what each does to history, the exact commands, how conflicts resolve, and the golden rule that keeps both safe. 💡 Quick Tips

Rebase Before the Pull Request: Clean your private branch with git rebase -i so reviewers read a tidy story, not your debugging trail.

Force-With-Lease, Never Force: git push --force-with-lease refuses to overwrite if a teammate pushed first — plain --force does not.

Merge on Shared Branches: On main and team branches, always merge. Shared history is a team record — keep it honest.

Frequently Asked Questions

When should I use git rebase instead of merge?

Rebase your private feature branch before opening a pull request — it produces a clean, linear history that reviewers can follow. Use merge on shared branches like main, where the true history is a team record nobody should rewrite.

Is git rebase dangerous?

Only on shared history. Rebasing commits that others have already pulled forces everyone to fix their branches. On your own unpushed branch, rebase is completely safe — abort anytime with git rebase --abort.

What is the difference between git pull and git pull --rebase?

Plain git pull merges the remote branch into yours, adding a merge commit. git pull --rebase replays your local commits on top of the remote ones instead, keeping a clean line. Many teams set pull.rebase true as the default.
