Pull Requests Chart: Printable GitHub PR Workflow Guide

A pull request is how code actually gets into a shared project: you branch off main, make your changes, and open a request that lets teammates review the diff, run the checks, and discuss the design before anything merges. The workflow has more moving parts than beginners expect — draft versus ready, squash versus merge commit, approvals, requested changes, and the conflicts that appear when main moves ahead of your branch. Guessing at any step stalls the review or, worse, merges broken code. This printable chart lists the twelve steps and commands of a clean GitHub pull request, from creating the branch to merging, with what each step does and when it happens. Consult the live reference table below, or print the sheet and keep it by your terminal.

💡 Quick Tips

Keep PRs small: One focused change per PR gets reviewed in hours; a 500-line PR sits for days and hides bugs.

Rebase before you merge: Rebasing onto latest main before merging keeps the history clean and catches conflicts early.

Review your own diff first: Read the Files changed tab first — you will catch typos and stray debug code yourself.

Frequently Asked Questions

What is the difference between squash merge and merge commit?

A squash merge compresses all PR commits into one commit on main, keeping history tidy. A merge commit preserves every commit and adds a merge commit, keeping the full history. Squash is best for small feature PRs; merge commits suit long-lived branches with meaningful commits.

How do I fix a merge conflict in a pull request?

Update your branch with git rebase main or git merge main, open the conflicted files, and keep the correct lines from each side. Remove the conflict markers, run the tests, then push — GitHub updates the PR automatically and the conflict warning clears.

When should I mark a pull request as a draft?

Mark a PR as a draft when the work is visible for early feedback but not ready for a full review — for example, when tests are still failing or the approach needs a sanity check. Drafts cannot be merged, so reviewers know the code is still moving.
